# 設定ファイルの判断

`claude-task-worker.json` / `plugin/.mcp.json` / `.claude/settings.json` など利用者へ配布・共有される設定と、利用者が import する公開APIに関する判断。

## 挙動を切り替えるフラグは未指定時に既存の挙動と同一になる側を既定にする

**適用条件**: 実行形態・機能の有効化・無効化など、既存の挙動を変えうるフラグ・設定キーを設定スキーマへ追加するとき

既定は未指定のリポジトリで挙動が変わらない側にする（新機能の有効化なら `false`、既存の対象を止める `enabled` なら `true`）。不正値は警告して既定へ倒す。あわせて「未指定の既存リポジトリで引数・cwd・環境変数・起動集合・テスト結果が変更前後で完全に同一」であることを不変条件テスト（既定値の全件走査＋出力のゴールデンテスト）で固定し、実装より先にマージする。理由は、既存利用者が設定を書き換えずに新機能の影響を受けないことが導入の前提であり、これを散文の約束ではなく機械的な検出力で守るため。

出典: #228, #421, #443

## 設定の適用単位は「対象ごとに違う値を選びたいか」で決める

**適用条件**: 新しい設定をワーカーなどの対象単位に置くか、トップレベル一括（またはコマンドのフラグ）にするかを決めるとき

対象ごとに違う値を選びたい設定（モデル・推論量など）だけを対象単位（`workers.<name>.<field>`）に置き、それ以外はトップレベル一括かコマンドのフラグにしてプロセス内で1回だけ解決・キャッシュする。対象ごとに適合性が違うことは対象単位に置く理由にならない。非対応の対象を既定の挙動へ落とす仕組みがあれば、一括指定のまま扱えるため。一括側を1回だけ解決するのは、実行中に判定が揺れると「引数の組み立て」と「実行経路」が食い違うため。

出典: #228, #243, #316

## 成立しない設定は起動時に拒否し、非対応・失効した指定は必ず可視化する

**適用条件**: 設定の組み合わせが機能的に成立しない、設定で指定したファイルが存在しない・読めない、一括指定の対象の一部が非対応・無効、または設定キーを廃止するとき

設定そのものが成立しない組み合わせや指定ファイルの不在は、タスクを1件も起動せずエラー終了させ、何が問題でどう直すかをメッセージに含める（判定は純粋関数として切り出し、ファイル読み取り・外部コマンド実行は呼び出し側に置く）。一括指定に含まれる個々の対象が非対応なだけの場合はエラーにせず既定の挙動のまま実行し、どの対象が落ちたかを起動時に1行ログで示す（`all` のような全対象起動コマンドには非対応の対象が必ず含まれ、対象単位の非対応をエラーにすると一括指定自体が使えなくなるため）。廃止した設定キーが残っている場合も無視で済ませず、移行先を示す警告を出す。いずれもサイレントに別経路へ倒さないためで、黙って倒すと利用者は指定した設定で動いているつもりのまま別経路の結果を受け取り、成果物が壊れるまで誤りに気づけない。

出典: #316, #423, #443

## 配布する設定へ個別ユーザーの認証情報を前提とする記述を入れない

**適用条件**: プラグインが配布する設定ファイル（`plugin/.mcp.json` 等）へ API キー・トークンを要する記述を足そうとするとき

環境変数の参照は未設定時に「無効化」ではなく「未展開の文字列をそのまま送る」挙動になるため、キーを持たない全利用者の機能後退になる。条件付きで省く手段が無い以上、個別の認証はユーザースコープの設定へ寄せ、配布物はキー無しで成立する構成に留める。理由は、マーケットプレイス配布物の変更コストは設定した一部ではなく設定していない全員が負うため。

出典: #276, #278

## 設定ファイル内の相対パスは、その値を書いたファイルの所在ディレクトリ基準で解決する

**適用条件**: 設定ファイルにパスを受け取るキーを足す、または設定ファイルを重ね合わせる・別の場所から読む経路を足すとき

相対パスは起動時の cwd ではなく、その値を定義したファイルの所在ディレクトリを起点に解決し、`~` はホームへ展開する。重ね合わせる場合は定義元が分からなくなる前（マージ前）にファイル単位で解決し、下流がリポジトリルート相対を前提にしている値はそこへ戻してから渡す。理由は、共有される設定ファイルは置き場所と起動ディレクトリが一致しないため、cwd 基準では書いた人が意図したファイルを指さなくなるため。

出典: #425, #443, #446

## 公開APIはエクスポート名をテストで固定し、変更を semver の破壊的変更として扱う

**適用条件**: 利用者のコードから import される公開エントリ（`claude-task-worker/lib`）へ export を足す、または公開済みのシンボルのシグネチャを変えるとき

公開するシンボルは名前付きで明示的に re-export し、エクスポート名の一覧をテストで固定する。内部ヘルパーも公開した以上、そのシグネチャ変更・削除は破壊的変更としてバージョンと影響範囲に明記する。理由は、利用者のワーカー定義は本リポジトリのテストに現れないため、公開面の変化がテスト失敗として見えないと利用者側で初めて壊れるため。

出典: #420, #424
