# 設定ファイルの判断

`claude-task-worker.json` / `plugin/.mcp.json` / `.claude/settings.json` など、利用者へ配布・共有される設定に関する判断。

## 挙動を切り替えるフラグは既定オフのオプトインにする

**適用条件**: 実行形態・機能の有効化など、既存の挙動を変えうるフラグを設定スキーマへ追加するとき

既定は必ず無効側（`false`）とし、不正値は警告して既定へ倒す。あわせて「フラグ未指定の既存リポジトリで引数・cwd・環境変数・テスト結果が変更前後で完全に同一」であることを不変条件テスト（既定値の全件走査＋出力のゴールデンテスト）で固定し、実装より先にマージする。理由は、既存利用者が設定を書き換えずに新機能の影響を受けないことが導入の前提であり、これを散文の約束ではなく機械的な検出力で守るため。

出典: #228, #230, #232

## 設定の適用単位は「対象ごとに違う値を選びたいか」で決める

**適用条件**: 新しい設定をワーカーなどの対象単位に置くか、トップレベル一括（またはコマンドのフラグ）にするかを決めるとき

対象ごとに違う値を選びたい設定（モデル・推論量など）だけを対象単位（`workers.<name>.<field>`）に置き、それ以外はトップレベル一括かコマンドのフラグにしてプロセス内で1回だけ解決・キャッシュする。対象ごとに適合性が違うことは対象単位に置く理由にならない。非対応の対象を既定の挙動へ落とす仕組みがあれば、一括指定のまま扱えるため。一括側を1回だけ解決するのは、実行中に判定が揺れると「引数の組み立て」と「実行経路」が食い違うため。

出典: #228, #243, #316

## 成立しない設定は起動時に拒否し、非対応・失効した指定は必ず可視化する

**適用条件**: 設定の組み合わせが機能的に成立しない、一括指定の対象の一部が非対応、または設定キーを廃止するとき

設定そのものが成立しない組み合わせは、タスクを1件も起動せずエラー終了させ、何が問題でどう直すかをメッセージに含める（判定は純粋関数として切り出し、ファイル読み取り・外部コマンド実行は呼び出し側に置く）。一括指定に含まれる個々の対象が非対応なだけの場合はエラーにせず既定の挙動のまま実行し、どの対象が落ちたかを起動時に1行ログで示す（`all` のような全対象起動コマンドには非対応の対象が必ず含まれ、対象単位の非対応をエラーにすると一括指定自体が使えなくなるため）。廃止した設定キーが残っている場合も無視で済ませず、移行先を示す警告を出す。いずれもサイレントに別経路へ倒さないためで、黙って倒すと利用者は指定した設定で動いているつもりのまま別経路の結果を受け取り、成果物が壊れるまで誤りに気づけない。

出典: #234, #239, #316

## 配布する設定へ個別ユーザーの認証情報を前提とする記述を入れない

**適用条件**: プラグインが配布する設定ファイル（`plugin/.mcp.json` 等）へ API キー・トークンを要する記述を足そうとするとき

環境変数の参照は未設定時に「無効化」ではなく「未展開の文字列をそのまま送る」挙動になるため、キーを持たない全利用者の機能後退になる。条件付きで省く手段が無い以上、個別の認証はユーザースコープの設定へ寄せ、配布物はキー無しで成立する構成に留める。理由は、マーケットプレイス配布物の変更コストは設定した一部ではなく設定していない全員が負うため。

出典: #276, #278
