# 設定ファイルの判断

`claude-task-worker.json` / `plugin/.mcp.json` / `.claude/settings.json` など、利用者へ配布・共有される設定に関する判断。

## 挙動を切り替えるフラグは既定オフのオプトインにする

**適用条件**: 実行形態・機能の有効化など、既存の挙動を変えうるフラグを設定スキーマへ追加するとき

既定は必ず無効側（`false`）とし、不正値は警告して既定へ倒す。あわせて「フラグ未指定の既存リポジトリで引数・cwd・環境変数・テスト結果が変更前後で完全に同一」であることを不変条件テスト（既定値の全件走査＋出力のゴールデンテスト）で固定し、実装より先にマージする。理由は、既存利用者が設定を書き換えずに新機能の影響を受けないことが導入の前提であり、これを散文の約束ではなく機械的な検出力で守るため。

出典: #228, #230, #232

## 設定の適用単位は「対象ごとに適合性が変わるか」で決める

**適用条件**: 新しい設定フィールドをトップレベルに置くか、ワーカーなどの単位ごとに置くかを決めるとき

対象ごとに適合性・可否が大きく違う設定はワーカー単位（`workers.<name>.<field>`）に置き、実行中に揺れると経路が食い違う設定はトップレベル一括にしてプロセス内で1回だけ解決・キャッシュする。理由は、一括設定は「引数の組み立て」と「実行経路」の不整合を防ぐ目的で存在し、適合性が個別に違う設定を一括にすると全体を最も適合性の低い対象に合わせることになるため。

出典: #228, #243

## 成立しない設定の組み合わせは起動時に拒否する

**適用条件**: 設定の組み合わせが機能的に成立しない、または対象が非対応と分かっているとき

タスクを1件も起動せずにエラー終了させ、何が問題でどう直すかをメッセージに含める。サイレントに別の実行形態へフォールバックしない。判定は純粋関数として切り出し、ファイル読み取り・外部コマンド実行は呼び出し側に置く。理由は、フォールバックすると利用者は指定した設定で動いているつもりのまま別の経路の結果を受け取り、成果物が壊れるまで誤りに気づけないため。

出典: #234, #239

## 配布する設定へ個別ユーザーの認証情報を前提とする記述を入れない

**適用条件**: プラグインが配布する設定ファイル（`plugin/.mcp.json` 等）へ API キー・トークンを要する記述を足そうとするとき

環境変数の参照は未設定時に「無効化」ではなく「未展開の文字列をそのまま送る」挙動になるため、キーを持たない全利用者の機能後退になる。条件付きで省く手段が無い以上、個別の認証はユーザースコープの設定へ寄せ、配布物はキー無しで成立する構成に留める。理由は、マーケットプレイス配布物の変更コストは設定した一部ではなく設定していない全員が負うため。

出典: #276, #278
