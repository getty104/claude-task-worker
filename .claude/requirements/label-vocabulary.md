# ラベル語彙とラベル遷移

GitHub ラベルを制御シグナルとして使う際の、語彙の追加と遷移の扱い。

## ラベルを追加したら必須ラベル定義と利用者向け表を同時に更新する

**適用条件**: 新しい制御用ラベル（`cc-*`）を導入するとき

`init` が作成する必須ラベル一覧と README のラベル表の両方へ追加する。既存の共起ラベルとの識別性（色の条件）も同時に満たす。理由は、ラベルが制御シグナルである以上、未作成のリポジトリでは付与に失敗して機構ごと動かず、表に無いラベルは人が手で救済する手段を持てないため。

出典: #284

## ラベル遷移・完了検証・通知の順序は実行形態に依らず同一に保つ

**適用条件**: 実行形態を増やす、または既存ワーカーの実行経路へ分岐を入れるとき

worktree の生成・cwd・起動引数は実行形態ごとに変えてよいが、ラベルの付与/除去・完了時の成果物検証・通知の呼び出し順は変えない。分岐は経路の内側に閉じ、外から見た状態遷移を1本に保つ。理由は、ラベルは他ワーカーのポーリング条件そのものであり、順序が形態ごとに違うと後続ワーカーが中途半端な状態のIssue/PRを掴むため。

出典: #235, #236, #237

## 止められないセッションを残す失敗では、ラベルを巻き戻さず人手確認へ倒す

**適用条件**: ワーカーから起動したセッションを停止する手段が無い実行形態で、起動確認・完了待機に失敗した、またはワーカー自体を停止するとき

トリガーラベルを戻して「未着手」に見せず、人手確認ラベルを付けたうえで対象 Issue/PR へ原因とセッションの所在（不明ならその旨）をコメントで残す。付与はワーカー共通の完了コールバックではなく失敗を確定させる箇所で行う（前者は同ラベルを付けないため、任せると誰も拾わない）。理由は、セッションが後から成果物やラベルを届けるため、未着手に見える対象へ成果物が届いて状態が読めなくなり、再ポーリングでセッションが量産されるため。

出典: #284, #306
